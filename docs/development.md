# 开发与验证

本文件给编码 Agent 一套可执行的修改流程。目标是让代码、配置、测试与文档始终表达同一个系统，而不是在任务结束时只留下能编译的局部补丁。

## 修改流程

1. 从 `docs/README.md` 找到模块边界和成熟度。
2. 检查真实源码、调用点、配置引用及当前 `git diff`。
3. 写下本次改动触及的契约：key、单位、协议、生命周期、安全状态、车型和验证层级。
4. 实现最小范围改动；纯逻辑尽量从硬件对象中提取，便于无硬件测试。
5. 公共接口、生命周期、协议、配置或成熟度变化与对应模块文档同步完成。
6. 先运行无硬件单元测试，再构建所有受影响车型；只有明确授权和安全环境下才运行主程序。
7. 检查最终 diff，区分自己的修改与用户已有改动，并在交付中如实说明未验证部分。

## 阅读与影响范围

改动前至少阅读 `docs/README.md`、`docs/architecture.md` 和对应模块文档。出现以下情况时扩大阅读范围：

- 改 `info_type`、key 或实例生命周期：同时读 Core、Config/Build 和所有调用方。
- 改报文或 byte 工具：同时读 IO、对应 Device、Utils 和配置。
- 改电机目标/反馈：同时读 Device、Control、Config/Build，核实物理单位与安全门。
- 改 Robot 状态：检查 Chassis、Gimbal、Shoot 及所有 `set_state` 调用点。
- 改模板/concept：全仓搜索实例化，并按四车型构建。

优先用 `rg` 查符号、字符串 key 和 CAN ID。语义化名称也是接口，不能只依赖编译器发现重命名遗漏。

## 实现模式

### 新增多例 IO/设备

1. 定义 `info_type::owner_type`、`key_type` 和 `key()`，保证 key 的存储生命周期覆盖整个进程。
2. 构造函数只验证自身参数和取得自身资源，不启动可能抢先运行的长期任务。
3. 如需跨实例绑定，实现幂等 `connect()`；如有长期协程，实现幂等 `start()`。
4. 在配置预检中检查 key、引用、ID、槽位、范围和必需参数。
5. 在 `src/main.cpp` 以依赖顺序加入构造、connect、controller init 和 start 阶段。
6. 有效反馈才刷新 `tick()`，并定义离线/禁用输出。
7. 添加无硬件的解析/校验测试及对应模块文档。

### 新增控制子系统

1. 用单例 `info_type` 接收依赖和参数；通过 `enable_*` 或等价配置明确车型是否启用。
2. 初始化时绑定 `motor_base*` 或其他设备抽象，不在循环中反复按字符串查找。
3. 把运动学、限幅、状态转移等纯逻辑提取到可单测函数。
4. 周期任务每条路径都必须 `co_await`，NoForce/离线/异常路径必须产生安全输出。
5. 在 Robot 统一编排启停，避免子系统各自发明不一致的安全状态。

### 修改协议

1. 先冻结帧格式：魔数、长度、key/ID、字段宽度、符号、端序、缩放、校验和和版本。
2. 避免直接复制外部字节到含 padding 或主机端序结构；必要时写独立 codec。
3. 覆盖短帧、超长帧、未知 key、错误校验和、粘包/拆包和重同步。
4. 更新 IO 与 Device 文档，并标明兼容性/迁移策略。

## 当前无硬件验证

```sh
xmake f -y -m debug --type=project
xmake build -y unit-tests
xmake run unit-tests
xmake build -y gkd-roboctrl
git diff --check
```

涉及配置公共结构或模板实例化时，应对 `infantry`、`hero`、`sentry`、`project` 全部重复 Debug/Release 构建。`tests/unit_tests.cpp` 不打开 CAN 或串口，可在无硬件环境运行。

测试使用 `assert`，Release 下通常定义 `NDEBUG` 时可能弱化断言，因此 CI 的 Debug 测试结果是逻辑检查主证据；Release 构建主要覆盖优化模式下的编译链接。若扩展测试框架，应让失败在所有构建模式都产生非零退出码。

文档验证至少包括：

```sh
git diff --check
find docs -type f -name '*.md' -print
rg -n '\[[^]]+\]\([^)]*\.md[^)]*\)' AGENTS.md docs
```

最后人工确认每个相对链接目标存在，成熟度描述与当前 `.cpp`、入口和配置一致。

## 运行与硬件安全

未经用户明确授权，不执行 `xmake run gkd-roboctrl` 或 `start.sh`。即使 Robot 默认 NoForce，主程序仍会打开总线和串口，电机组任务也会周期发送零电流帧；设备配置、固件或接线错误仍可能带来风险。

获得上机授权后也应分级推进：先只读/断执行器验证报文，再架空轮台架验证方向与零输出，最后在可急停场地验证状态机。每一级记录车型、配置、硬件版本、命令和观察结果。

## 文档同步判定

下列变化不是“仅实现细节”，必须更新文档：

- 新增、删除、重命名模块、类、长期任务或配置 key。
- 修改初始化/connect/start 顺序、失败传播或所有权。
- 修改报文、CAN ID、串口 key、单位、缩放、PID/Ramp 或轮速符号。
- 修改 NoForce、离线、enable/disable 或功率限制行为。
- 改变某模块从骨架到部分实现/已接入，或发现已有功能实际不可用。
- 修改构建依赖、车型矩阵、测试和部署工作流。

纯格式、拼写或不改变语义的局部注释可以不更新模块文档，但仍需确认文档不因此失真。若代码与文档冲突，不要删除限制性描述来“让它一致”；先确认代码变更是否真的完成并被测试。

## 提交边界

- 保留用户已有未提交修改，避免混入无关重构。
- 未实现的云台循环、发射状态机、M9025、功率管理和裁判系统继续标为骨架或部分实现。
- “单元测试通过”不等于“实车安全”；报告必须单独说明是否完成 Linux 构建、台架和实车验证。
- 不因文档任务顺手修复源码问题；发现问题时记录事实和最小影响，只有用户要求实现时才改代码。
